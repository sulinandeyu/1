# Build 29 摄影审美目标与自动参数决策整改

日期：2026-11-09

证据包：`XiaoSuCamera_Diagnostic_20261108_212040_411c710221.zip`

证据来源：真实 iPhone Build 29 诊断导出；A/B/D/M 均为 2160×2880 同源 JPEG。

> 本报告区分 Windows 像素复核、Swift 代码实现、远程 iOS 编译和 iPhone 人工审美。Windows 统计不等于 Core Image 或真机验收；技术质检通过不等于摄影审美通过。

## 2. 根因

### 2.1 为什么 Build 29 D 更亮

Build 29 D 改为源图相对目标。原图分析亮度约 `0.637`，D 目标约 `0.605`，最终约 `0.613`；曝光仅 `-0.0058 EV`、亮度 `-0.0024`。Build 28 D 更接近正式 B 的强度，因此更暗。Build 29 的变化方向符合新目标，但目标本身过于连续、保守。

### 2.2 为什么 92.6% 目标达成仍不好看

`92.6%` 衡量的是结果是否接近当前 D 自己定义的亮度、反差和饱和度目标。当前目标把源图相对亮度保留得较多，同时把目标反差设为约 `0.660`；渲染结果的反差被压到 `0.774`。因此系统能够高分完成一个偏平的目标，却没有证明该目标具有摄影审美价值。

原实现还存在两个放大误判的因素：

- `AestheticPhotographyPlanner` 将无可靠主体场景的规划置信度硬抬到 `0.42`，这一数字不是证据置信度。
- D 只有一个目标假设，候选选择主要评价技术风险和该目标残差，不能比较“自然连续”“空间强调”“克制暗调”哪一个更合理。

### 2.3 为什么颜色协调很弱

虽然植被黄色比例约 `0.509`，D 的黄色 HSL 只有约 `+0.0373`，植被局部饱和仅约 `1.005`，颜色分离目标约 `0.030`。颜色证据经过目标、规划、求解器安全边界和蒙版混合多层约束后，最终只产生轻微变化。Build 29 D 植被饱和度 `0.2971`，低于 B 的 `0.3451`；这说明识别和执行都存在，但目标没有形成足够明确的综合色彩关系。

### 2.4 第二轮反馈是否触发

Build 29 ZIP 无法证明。旧版详情内部曾生成反馈状态，但 `DiagnosticCandidateEvidence` 的导出关键词没有保留“同定义复测”“有限反馈”“最终实际参数”，因此 ZIP 只保存了最终 D 参数，没有保存反馈是否生成、采用或拒绝。不得根据最终图片反推。

## 3. 本轮代码整改

### PT-AESTHETIC-005：逐图目标假设

新增诊断专用 E1/E2，不按场景名取固定参数：

- E1“动态空间层次”：由当前图亮度、反差、可恢复高光、噪声余量、可靠区域覆盖和区域颜色关系求解。
- E2“动态克制暗调”：由当前图暗调余量、端点压力、噪声、氛围保护和可靠蒙版求解，并以源黑位为硬边界。

二者都复用现有 `AestheticPhotographyPlanner`、`AdaptivePhotographyParameterSolver`、全分辨率 `CoreImageRenderer`、区域影响测量和技术质检。它们不是 LUT，也没有“秋季道路”条件分支；同一场景不同曝光会得到不同目标。

### PT-AESTHETIC-006：三层评价分离

候选证据现在分别记录：

1. `technicalQualityStatus`：裁切、偏色、噪声、蒙版等技术风险。
2. `targetQualityStatus`：当前目标是否有足够依据；无人工证据时为不确定。
3. `humanAestheticStatus`：人工盲测状态；未评价时明确为待评价。

目标达成率不再被呈现为审美成功率，E1/E2 不自动选赢家、不替换 B。

### 执行证据与诊断导出

- D/E1/E2 记录首轮与最终同定义测量、反馈 `generated/adopted/rejected/failed/notGenerated`、最终实际配方和区域实测。
- ZIP 增加 E1/E2 全分辨率图片及状态；C 仍严格遵循许可门控。
- 相册导出按候选记录的 exact stage name 取图，避免旧预览混入。
- 人工偏好工具支持 A/B/C/D/E1/E2/M，并单独记录技术、目标质量、问题标签和人工确认。

### M v4 表达验证

M v3 的主要失败证据是全图 5–95% 跨度 `0.9523`；植被和建筑跨度分别约 `0.9540/0.9130`，树冠和建筑暗部的黑位明显增加。v4 不放宽质检阈值，而是取消黑点、降低曲线和局部对比、提高有限阴影恢复、降低 HSL 与锐化强度。M 仍仅用于验证渲染器表达能力，不进入自动算法。

## 4. 当前可以与不可以下结论的事项

- 可以确认：Build 29 D 比 Build 28 D 更亮，是源图相对目标和更弱曝光造成；不是保存错误。
- 可以确认：Build 29 D 技术通过，但没有形成优于 B 的已验证审美；从本例看只是实现了不同且更保守的数值目标。
- 可以确认：M v3 证明渲染器能够形成明显影调与颜色变化，但该组合过硬，不能作为合格成片。
- 尚不能确认：E1、E2 或 M v4 是否优于 B。它们必须先通过远程 Swift/iOS 编译，再由新的 iPhone 诊断 ZIP 和盲测验收。
- 尚不能自动判断：无可靠主体时哪种摄影方向最好、强弱表达的个人偏好、参考作品氛围是否适合当前真实场景。这些状态会明确保持为不确定，而不是伪造高分结论。
