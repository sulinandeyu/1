## 录屏与代码交叉验证

1. 录屏顶部选中“AI 成片”时，代码 `PhotoPreviewView.displayedImage` 读取 `photo.editedImage`。`PhotoProcessingPipeline` 把正式最终结果写入 `editedImageData`，因此顶部“AI 成片”是 **B 正式算法**，不是 D。
2. 顶部“差异”读取 `photo.differenceImage`；该差异由正式 A 与 B 生成，不代表 D 或 M。
3. D 只在“逐阶段像素预览”的 `D 新版逐图自动后期（passed）` 项中显示。录屏记录 `renderStatus=completed`、`technicalQualityStatus=passed`、`eligibleToReplaceB=false`，证明 D 已全分辨率渲染并通过技术门，但没有替换 B。
4. C 在录屏中因参考索引/许可门控不可用而跳过，没有生成伪造 C 图片。
5. M 为独立人工参数渲染验证；它不参与正式 B 决策，也不会替换 B/D。

## Build 27 实际分析证据

录屏可读出的可靠区域覆盖约为：植被 42.3%、地面 32.8%、天空 10.4%、建筑 1.5%。同时类级语义主体把车辆选为优先对象，置信度约 89%，覆盖约 13%。这说明分割确实执行，但“存在可靠区域”不等于“摄影主体判断正确”。

D 的录屏参数显示：

- 整体实测亮度约 0.637，目标约 0.584。
- 全局曝光约 -0.039 EV，亮度约 -0.016。
- 天空曝光约 -0.07 EV，高光约 0.58，饱和度约 1.01。
- 橙色饱和约 +0.04；黄色 H/S/L 基本为 0；绿色基本为 0；青色约 -0.02；蓝色约 -0.03。

因此本次 D 不是“没有渲染”或“质检回退”。更直接的问题是：

1. 类级车辆区域在广覆盖环境构图中取得主体优先，摄影目标偏向车辆，而不是树冠、道路和空间层次的整体关系。
2. 旧区域统计只有平均 RGB、亮度、饱和度，没有黄色比例测量；求解器在本图中没有形成黄色叶片的颜色目标，黄色 HSL 接近零。
3. 区域曝光和局部对比受置信度、区域响应和安全上限多次衰减，结果技术安全但视觉表达偏弱。
4. D 是单独诊断候选，不参加 B 的三候选选择；因此本次 D 效果弱不能归因于“候选评分选回原图”。

原图与参考图同为 2160×2880，但参考图并非可直接复制的标准。辅助像素统计显示：

## 本阶段通用修复

- 诊断 UI 明确标记 `A 原图`、`B 正式成片`、`A↔B 差异`，选中阶段时直接显示 D/M 的完整阶段名。
- 新增一键诊断 ZIP，导出同源 A/B/D/M、单参数探针、蒙版、结构化状态与参数、质检、耗时、内存、App/Build/设备/iOS 信息；C 不可用时只写 unavailable 记录。
- 当可靠环境区域广泛覆盖画面时，小覆盖的非人物/动物/食物类级区域不再自动证明摄影主体，改为全图与区域关系协调。该规则不针对车辆或秋季街道硬编码。
- 在可靠区域内增加黄色/绿色颜色比例测量。黄色 HSL 由当前照片的黄色比例、区域饱和度余量和亮度关系动态求解；颜色比例不等于物体身份。
- M 改为诊断专用的空间与颜色表达验证组合，用于验证天空、高光、亮度范围、黄色/绿色 HSL 和局部区域链能否实际产生可感知结果；它仍不是正式模板。

## 仍需新 Build 真机验证

- 新的主体门控是否不再把低覆盖车辆当成摄影主体。
- D 黄色参数是否来自本图测量，并真实进入 Core Image 全分辨率渲染。
- M 是否能证明渲染器具备更强但仍安全的影调和颜色表达能力。
- ZIP 中 A/B/D/M 是否均为同一原图的实际输出，状态和实际执行记录是否一致。
- 自动技术质检通过不代表审美合格，仍需对实际 A/B/D/M 做人工盲测。
