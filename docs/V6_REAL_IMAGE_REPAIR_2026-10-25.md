## 3. 已确认根因与代码证据

### 根因 1：小人物让整个环境画面提前进入人像主策略

旧 `SceneStrategy.choose` 在检测到 portrait facet 后立即返回 `.portrait`。这张照片中人物面积小，主要画面是天空和山体，但风景策略、天空策略的完整分支因此无法执行。人物保护本身是正确的，错误是把“有人”误当成“整张照片由人像主导”。

### 根因 2：明亮蓝天可能被误判为蓝调时刻

旧 `PhotographyContext.make` 只要天空占比大、全图亮度低于 0.52、蓝通道高于红通道，就加入 `.blueHour`。这张日间蓝天照片的全图亮度和偏蓝关系可能满足该条件，导致系统压制蓝/青饱和度并采用错误的时间氛围。

### 根因 3：风景动态范围使用固定压缩方向

旧 `.landscape` 无条件把 `highlightAmount` 压到 0.72、把 `shadowAmount` 抬到至少 0.14。即使原图没有高光裁切或暗部堵塞，也会缩小山体与前景亮度跨度。真实区域指标与这一处理方向一致。

### 根因 4：天空参数使用全图统计

旧 `applySkyStrategy` 用全图饱和度、对比度和高光占比决定天空强度。人物、山体和前景会稀释天空统计，不能回答“天空本身是否已经饱和、是否需要恢复云层”。

### 根因 5：环境人像的全局偏色可能被当作人像色偏

旧 `PhotoProblemDetector` 因 `semanticScene` 对任何有人脸照片优先返回 portrait，会把蓝天造成的全局蓝色关系解释为需要纠正的人像冷偏，潜在地对整个风景加暖。

## 4. 实际代码修复

- `PhotoAnalyzer`：在可靠语义蒙版内计算天空、地面、植被、水面、建筑的真实亮度、5–95% 对比、RGB、饱和度、暗部和高光占比。
- `PhotoAnalysis`：保存区域统计，记录人物蒙版覆盖率和最大人脸覆盖率；日志新增天空区域指标。
- `PhotographyContext.make`：蓝调时刻要求真实低照度/暗部证据或明确时间标签；明亮天空记录为 daylight/midday，不再仅凭偏蓝判定蓝调。
- `SceneStrategy.choose`：可靠人物蒙版存在且人物/人脸占比较小时，允许环境主导的风景、城市、建筑策略；`enforcePortraitProtection` 仍然最后执行。
- `PhotoProblemDetector`：环境人像不再根据全图蓝天/植被色彩执行中性色偏校正。
- `PhotographyDecisionEngine`：天空参数使用天空区域统计；风景高光和阴影只在实测裁切/堵塞时恢复，并根据原始对比度决定层次强度。
- `LocalAdjustmentProcessor`：山体/自然地面已有层次时限制抬曝光、提高蒙版内局部对比；平坦且确有可恢复暗部时才提升阴影。
- `PhotoDiagnostics`：真机面板新增人物/人脸覆盖率和天空区域实测值。

## 5. 自动测试与证据边界

新增决策回归覆盖：

1. 小人物山景进入 landscape 主策略，同时人物保护保持严格启用。
2. 明亮蓝天不会误判为 blue hour。
3. 无裁切的风景不再固定压高光/抬阴影；真实裁切照片仍会恢复高光。
4. 环境人像不会把天空冷色误判为需要全局纠正的人像偏色。
5. 区域统计只读取蒙版内像素，不被蒙版外颜色污染。

## 6. 如何证明不是统一滤镜

真机诊断必须同时满足以下证据：

1. 不同照片的 `sceneFacets`、lighting、style 和主策略与内容一致，而不是仅参数 JSON 不同。
2. 日间蓝天人物山景应记录 `landscape + environmentalPortrait + midday`，且人物保护 active；蓝调人像应记录 blueHour，室内/夜景不得复用该组合。
3. 诊断面板必须出现各自区域的实际统计、蒙版覆盖率和执行/跳过原因。
4. 最终配方必须与渲染器收到的配方一致；区域处理必须在执行回执中出现。
5. 导出的新 JPEG 需要按区域检查：天空、地面/山体和人物的变化方向与决策一致。只有全图都出现同方向青蓝变化时，应判定失败，即使整体 MAE 达标。
